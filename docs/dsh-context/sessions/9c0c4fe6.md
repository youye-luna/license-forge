## 用户诉求

- 以数据源调研员身份，为本项目的开源许可证生成工具补齐结构化条款数据（现状：740 个 SPDX 许可证里只有 32 个精校了条款字段，其余靠正则从正文推断，不可靠），用 web_search / web_fetch 实际访问并验证候选数据源。
- 重点要找 5 类数据：许可证分类（permissive / copyleft / weak-copyleft / public-domain 等权威分类）；条款布尔字段（专利授权、商标条款、要求标注改动、网络触发、文件级 copyleft）；OSI/FSF 认证状态（已有 SPDX，确认是否有更权威来源）；兼容性矩阵；许可证「使用场景/适用范围」标签（软件/内容/硬件/字体/数据）。
- 必须实际访问验证的候选源：ScanCode LicenseDB（含 help 页，重点看 category、is_exception、owner、short_name、other_spdx_license_keys 字段，并试 `licenses.json` 之类端点）；OSI 官方 API（从 discuss.opensource.org 公告找端点并验证）；FSF/GNU 许可证清单及其结构化可用性；SPDX license-list-XML 仓库（除正文外的 isOsiApproved、isFsfLibre、crossRef、standardLicenseHeader，以及有无「类别」信息）；Blue Oak 及其他提供条款维度结构化数据的项目（如 license-compatibility、choosealicense 的 _licenses YAML front matter）；REUSE / ClearlyDefined（是否有 API 提供许可证元数据与分类）。
- 每个源输出：名称 + **亲自 fetch 成功并看到内容的实测可用 API/数据 URL**；HTTP 状态、响应体积、数据格式；真实字段名清单；覆盖范围（多少许可证、是否覆盖 SPDX 740、覆盖率）；该数据源自身的许可证与授权情况；缺点/风险（字段缺失、维护状态、与 SPDX ID 映射可靠性）。
- 最后一节给出「推荐的数据源组合方案」：哪个源负责哪些字段、如何与 SPDX ID 映射、需要注意的坑（SPDX ID 与 ScanCode key 不一致、例外条款处理、废弃标识符）。

- 三个必须知道的坑（会话结论）：
  - `api.opensource.org` 的 `approved` 字段**不是 OSI 认证**——126 条里只有 7 条 true、119 条 false；若用它覆盖 SPDX 的 `isOsiApproved`（154 true）会毁掉数据；该 API 只能补 `submission_date` / `board_minutes`。
  - ClearlyDefined 不可用——`/definitions` 返回的是组件坐标分页而非许可证字典，所有 `/definitions/license/*` 变体 404 或超时，已建议放弃。
  - LicenseDB 的 `licenses.json` 是 404——真实索引叫 `index.json`（扁平数组，非 `{licenses:[]}`）；要全字段得逐 key 拉 2733 次。
- 意外收获：ChooseALicense 的 `_data/rules.yml` 即条款本体（5 permissions + 8 conditions + 4 limitations），标签直接对应目标布尔字段（`document-changes`=标注改动、`network-use-disclose`=网络触发、`same-license--file`=文件级 copyleft、`limitations.trademark-use`=商标），但 `patent-use` 在 permissions 与 limitations 中**同名反义**；GNU 清单的 4 个 h3 章节是全网唯一权威「适用范围」来源（文档/其他作品/字体），但 gnu.org 从本机 TCP 层不可达，改用 GNU 官方 ftp 镜像 `ftp1.gwdg.de` 取得 63 KB HTML（纯 `<ul><li>`，无 table、无结构化版本，需自写解析器）；OSADL 的 `explanation` 字段为每一对兼容性附法律理由，可直接作为 UI 提示文案。
- 计数校正：SPDX 索引实际为 **786** 条（含例外/废弃项），而 `licenses.json` 为 740；`isFsfLibre` 仅 147/740 标注（其中 127 true）；GitHub licenses API 仅 13 条，过窄不可用。
- 最严重的现实约束：条款布尔字段的精确数据只覆盖 **47–225 个许可证（6%–30%）**，剩余 500+ 必须保留 `confidence: inferred` 标记，不可把正则推断写成确定值。

## 结论与遗留

- 达成结论：**没有任何单一数据源提供「条款布尔字段」**，必须组合 5 个源——LicenseDB（分类/例外/owner）、SPDX（全量 ID、isOsiApproved、isFsfLibre、crossRef、standardLicenseHeader）、ChooseALicense rules.yml（条款布尔本体）、OSADL（兼容性矩阵 + 法律解释文案）、Blue Oak（分级评级）；GNU 清单补「适用范围」，OSI API 仅补提交/批准日期。
- 明确决定：放弃 ClearlyDefined 作为许可证元数据源；不使用 `api.opensource.org` 的 `approved` 覆盖 OSI 认证状态；精确条款数据与推断数据必须分离标记（`confidence: inferred`）。
